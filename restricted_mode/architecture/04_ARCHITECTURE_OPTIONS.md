## Рекомендация по последовательности

1. AUTH-01 выполнен, D01 принят. Составить карту обходов T1 (EXT-01), уточнить видимость D02 и ожидаемое поведение уведомлений D03; проверить policy на всех штатных путях.
2. STORAGE-01: замкнуть inventory на `.tempkey`, metadata/atomic-state, PIN, login tokens, notification/auth backup, media/temp/WAL; проверить независимый envelope на синтетическом контейнере.
3. NOTIFY-01 и SYNC-01: проверить платформенные пределы и восстановление, затем LIFE-01.
4. Сравнить B/C по результатам, а не по размеру UI patch. Проигравший вариант отклонить в ADR с доказательствами.

Общий raw Account содержит Network, Postbox и фоновые операции (E13). Передать его UI Restricted с декоративной policy означает оставить обходы. С другой стороны, низкоуровневая фильтрация Postbox без семантики peers/references/cursors может повредить состояние. Нужны совместно проверяемые границы выдачи, действий, ingress и persistence.

## Критерии отказа от кандидата

- Не может выполнить обязательный T-уровень без исключения, которого владелец не принимал.
- Открывает FullStore/ключи через AccountManager, backup, extension или background.
- Не позволяет безопасно отменить старую сессию или восстановиться после crash.
- Требует терять Full данные при поведении, для которого владелец требует сохранность.
- Не обеспечивает обязательное поведение уведомлений с доступной подписью.
- Сохраняет скрытые peers/content в Restricted cache/metadata, даже если список чатов выглядит правильно.

Ни B, ни C не получили PASS. Два хранилища — проверяемая гипотеза, а не обязательство реализации.
