|---|---|
| Создание visible | Финальный запрос вернул канал с точным title и отсутствующим username; владелец открыл visible |
| Создание hidden | Получен канал с ожидаемым уникальным title, access hash и отсутствующим username |

| Прямой `getHistory` после отказа | Вернул hidden canary с той же пользовательской авторизацией |
| Адресный `getPeerDialogs` | Вернул hidden canary |
| `messages.search` внутри hidden peer | Вернул hidden canary |
| Новый контекст без пользовательской авторизации | Тот же адресный `getHistory`: **401 AUTH_KEY_UNREGISTERED** |

Локальная проверка allowed set — модель policy эксперимента. Она не является реализацией защищённого Restricted Mode. Прямой вызов намеренно не использует эту проверку. Наблюдения подтверждают возможность чтения проверенного cloud channel при доступе к обычному авторизованному Network. Они не доказывают обход будущей криптографической изоляции, извлечение ключей T2 или полноту покрытия всех API.

## Ограничения и отклонения процедуры

Первый callback менял value-type persistent переменные LLDB; последующие выражения изменений не увидели. Итог первого запроса создания visible неизвестен. Для остальных запросов использован общий NSMutableDictionary, обновляемый на main queue. Первоначальное подтверждение владельца относилось к hidden: после открытия Simulator владелец уточнил, что в списке только hidden. Открытый экран также проверен на точное совпадение hidden title. Только после этого visible создан повторным запросом с сохранением результата; получены handle, успешные sendMessage и getHistory. Глобальная инвентаризация аккаунта не выполнялась; отсутствие дополнительного канала от первого запроса серверным перечислением не подтверждалось.

Для восстановления первого handle выполнялись локальные поиски по тестовому имени/префиксу и `contacts.search` с полным уникальным тестовым именем. Они не дали handle. Это дополнительный поиск метаданных по тестовому запросу; глобальные `getDialogs`, `searchGlobal` и чтение личной истории не выполнялись. Результаты пользовательских объектов не печатались и не сохранялись.

На время запросов выключены Logger.logToFile и Logger.logToConsole. Отрицательный MTContext использует собственный handshake без пользовательской авторизации и без личного keychain. Попытка с transport `useUnauthorizedMode=true` не дала результата; после исправления на обычный MTProto handshake получен явный 401. Отсутствие ответа не засчитывалось как успешный контроль.

После опыта подписки стенда disposed, запрос отрицательного контроля удалён из его request service, отдельный MTProto остановлен. Исходные logger flags восстановлены и проверены (`logging_restored=true`). LLDB detached; приложение продолжает работать, окно Simulator открыто. Auth keys, peer IDs/access hashes и личный контент не экспортировались. Временные LLDB объекты могут оставаться в памяти до завершения процесса; перезапуск приложения и очистка контейнера не выполнялись.

Visible baseline выполнен после hidden probes: финально оба canary прочитаны. Не проверены session restart, ротация/отзыв полномочий, список диалогов всего аккаунта, secret chats, media, другие API, физическое устройство, T2 extraction и будущая production граница. Независимое review отсутствует. Source hash отдельного harness отсутствует: использованы интерактивные JIT-выражения, процедура сохранена в README; это ограничивает автоматическую воспроизводимость.

## Архитектурное следствие

ACR-001 получает runtime свидетельство: фильтрация и локальный allowlist не ограничивают серверные полномочия доступного авторизованного Network. Proposed ADR-001 остаётся Proposed. Для требований, исключающих использование hidden authority из Restricted runtime, требуется отдельное решение о границе полномочий; этот опыт не разрешает ослаблять I01/I06.
