# AUTH-01: план эксперимента на аккаунте владельца

Дата: 2026-09-27. Base SHA: `42a84aec8abf72e54958ddf8ca9480514cc0d390`.
Статус: **эксперимент запущен на существующей сессии владельца в Simulator**. Результаты: [AUTH-01_RESULT.md](AUTH-01_RESULT.md).

## Разрешение и границы

Владелец явно поручил выполнить AUTH-01, использовать его аккаунт и создать два приватных тестовых канала. Это уточняет исходное задание, предполагавшее отдельные тестовые аккаунты A/B. Использовать личную переписку для эксперимента не требуется и не разрешается этим планом. Незавершённые процессы предыдущего прохода не считаются текущей авторизованной сессией.

Только два вновь созданных приватных канала с синтетическими сообщениями, без подписчиков, публичного username и приглашений. Создание каналов и публикация тестовых сообщений разрешены владельцем. Удаление каналов/аккаунта, отзыв других сессий, изменение настроек безопасности и чтение других диалогов в scope не входят. Каналы остаются после эксперимента, их наличие будет отражено в отчёте.

Файлы реализации: при необходимости `Tests/RestrictedModeExperiments/` (test-only harness и BUILD); документы и обезличенные результаты — `restricted_mode/architecture/`. Production code/BUILD, local-config, signing, entitlements и зависимости не менять. Исследованные механизмы повторного использования: Network.request, TelegramApi, Account/accountWithId и Tests/Common/Main. Существующий test_loginAndDeleteAccount неприменим: он включает console logging и удаляет аккаунт.

## Гипотеза и модель кандидата

Проверяется только гипотеза: локальное исключение диалога из разрешённого набора при сохранении обычной авторизации Telegram не позволяет запросить историю этого диалога напрямую.

Full fixture и кандидат Restricted используют одни серверные полномочия. Метка hidden относится к policy эксперимента, а не к существующему защищённому режиму Biremis: такого режима ещё нет. Эксперимент не доказывает обход будущей криптографической изоляции или отсутствие обходов всех API.

## Последовательность

1. Установить, где владелец уже авторизован, и выбрать изолированный способ выполнения. Не искать и не копировать auth keys из личных контейнеров. При необходимости использовать отдельный вход через UI, без кодов/паролей в чате и логах.
2. Зафиксировать среду, SHA и hash экспериментального исходника; отключить логирование request/response content. Не запускать обычный Account runtime, который автоматически синхронизирует личные диалоги, без отдельной оценки его side effects.
3. Создать два приватных канала с уникальным префиксом `AUTH-01`, сохранить только их handles в локальном состоянии эксперимента. Никакой публичной ссылки и подписчиков.
4. Отправить в каждый канал по синтетическому canary-сообщению; проверить доступ Full к обоим через getHistory. Серверные ID/access hashes нужны только в памяти/локальной fixture и не входят в публичный отчёт.
5. Локальная policy кандидата разрешает visible и запрещает hidden. Проверить отказ policy guard для hidden; затем непосредственно вызвать Network.request(getHistory) с теми же полномочиями, минуя guard.
6. Проверить hidden через адресные getPeerDialogs и messages.search для **этого** peer. Глобальные getDialogs/searchGlobal не использовать: они могут вернуть личную переписку. Это ограничение фиксируется как отличие от полного discovery scenario.
7. Отдельный контекст без пользовательской авторизации выполняет тот же адресный запрос. Ожидается отказ авторизации; timeout, неизвестный peer/access hash или другая ошибка не считаются подтверждением отрицательного контроля.
8. Сохранить только имена шагов, типы ответов, booleans совпадения canary, разрешённый код ошибки, SHA и среду. Не сериализовать messages/users/chats, ключи, номер телефона, коды входа или настройки API.

## Значение результата

- Full читает оба canary, guard запрещает hidden, прямой RPC возвращает hidden canary, unauthed control даёт отказ авторизации: гипотеза о защите одной локальной policy опровергнута для проверенного пути.
- Нет успешного Full baseline, нет контролируемой сессии или не завершён отрицательный контроль: данных недостаточно, не PASS защиты.
- T3: проверка использования полномочий без извлечения ключа. T4: модель произвольного RPC из тестового кода; не доказательство доступа debugger к реальному приложению. T2 extraction не выполняется.
- I01/I06 не ослабляются; результат обновляет ACR-001 и Proposed ADR-001. Архитектуру/угрозы принимает владелец отдельно.

## Проверка плана перед кодом

Проверены scope, разрешение на создание fixture, отсутствие destructive cleanup, защита секретов и ограничение чтения двумя созданными peers. Владелец указал существующую сессию этого форка в Simulator. Использован живой Account.network через LLDB, без копирования auth keys и без переустановки приложения. Обычный runtime приложения продолжает собственную синхронизацию; эксперимент не управляет её содержимым. Независимое review другим агентом не проводилось; несколько агентов автоматически не запускаются.

Отрицательный контроль выполняется через новый MTContext/MTProto в памяти, без подключения личного keychain и без входа в аккаунт. Переиспользуются сериализация протокола, encryption provider, API environment и адрес DC; auth info и auth tokens не копируются. Обычный MTProto handshake создаёт собственный транспортный ключ, который не авторизован как пользователь. `useUnauthorizedMode` обозначает транспортный режим до handshake и для прикладного RPC не используется.
